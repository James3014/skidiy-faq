# SKIDIY 平台重構計畫：緣起、分析與最終藍圖

**文件版本**: 1.0
**日期**: 2025-10-15

---

## 1. 緣起：為何要重構？ (The "Why")

本計畫的啟動，源於對現有 `diy.ski` 平台及內部工具（FAQ 系統）的全面評估，旨在解決一系列挑戰，並為未來的業務發展奠定堅實的技術基礎。

### 1.1. 現有 `diy.ski` 網站的挑戰

- **不利於搜尋引擎優化 (SEO)**：目前的網站內容主要由 JavaScript 動態載入，導致搜尋引擎難以抓取和索引頁面內容，影響了自然流量的獲取。
- **內容呈現單一**：現有的「長篇指南」格式雖然詳盡，但缺乏互動性與現代化的版面設計，難以在第一時間吸引使用者，或讓使用者快速找到所需資訊。
- **內容維護困難**：缺乏一個非技術人員也能輕鬆上手的後台編輯系統，增加了內容更新的門檻與時間成本。

### 1.2. 現有 FAQ 後端系統的優勢與侷限

在分析內部 FAQ 系統後，我們發現了巨大的潛力與一些待解決的問題。

- **優勢**：它不僅僅是一個 FAQ 系統，而是一個功能強大的 **Node.js/Express 後端服務**，已經具備了內容 API、數據分析、CRM 日誌等多項核心功能。這是一筆寶貴的現有資產。
- **侷限**：
    1.  **安全缺口**：後台管理的 API (`/api/v1/admin/*`) 缺乏統一的身份認證和權限管理，存在安全風險。
    2.  **資料儲存**：核心內容儲存於 `.json` 檔案中。這種方式在多人協作、即時編輯的後台系統場景下，會遇到效能和資料一致性的瓶頸。
    3.  **功能不全**：缺少對新內容類型（如教練、文章、優惠）的管理 API，也缺少通用的使用者行為追蹤 API。

## 2. 最終架構：我們的策略是什麼？ (The "What")

基於以上分析，我們確立了最終的重構核心策略，以求在最大化利用現有資產的同時，徹底解決所有已知問題。

### 2.1. 核心策略：重用後端，革新前端

我們**不**從零開始打造一切。我們將：
1.  **重用並強化**現有的 Node.js/Express 後端服務，將其作為整個平台的中央 API 伺服器。
2.  **全新開發**兩個基於 **Next.js** 的現代化前端應用，以徹底革新使用者體驗。

### 2.2. 三大系統元件

我們的平台將由以下三個獨立但緊密協作的應用程式組成，並以 **Turborepo** 管理的 **Monorepo** 結構進行開發：

1.  **`apps/web` (前台網站)**：面向大眾的公開網站。使用 Next.js 的伺服器端渲染 (SSR) 功能，確保絕佳的 SEO 與載入效能。它將負責所有豐富的內容呈現與使用者互動。
2.  **`apps/admin` (後台介面)**：一個統一、安全的管理後台。它將取代所有舊的、分散的管理頁面，提供內容管理 (CMS) 與數據分析儀表板兩大核心功能。
3.  **`backend` (後端服務)**：現有的 FAQ 系統。我們將在其基礎上進行強化，為上述兩個前端應用提供所有需要的 API 服務。

## 3. 後端更新計畫：如何強化現有服務？ (The "How" for the Backend)

為了支撐全新的前端應用，我們需要對現有後端進行以下幾項關鍵升級：

### 3.1. 實作統一的 API 安全認證
- **目標**：保護所有後台管理相關的 API。
- **做法**：新增一個「認證中介層」，對所有 `/api/v1/admin/*` 的請求進行攔截，驗證請求者是否具備管理者身份的 JWT (JSON Web Token)。

### 3.2. 為新功能新增 API 端點
- **目標**：滿足新前端的資料需求。
- **做法**：開發新的 API，包括：
    - 內容相關：讀取 `.md` 敘事內容的 API、教練/文章/優惠的 CRUD API。
    - 分析相關：接收使用者行為的通用事件追蹤 API (`/api/v1/events/track`)、對 FAQ 系統提供的匯總洞察端點 (`/api/v1/analytics/faq-insights`)，並統一使用 `/api/v1` 版本化路徑與 API key 授權機制。

### 3.3. 規劃資料庫升級路徑
- **目標**：解決檔案型儲存的瓶頸，為未來的擴展性做準備。
- **做法**：
    - **短期**：新增的內容類型可暫時繼續使用 JSON 檔案儲存，以求快速實現。
    - **長期**：規劃在未來將所有內容從 JSON 檔案遷移至 **PostgreSQL** 資料庫，並引入 **Prisma** 作為 ORM，以實現端到端的型別安全和更高效的資料操作。資料倉儲同時會由專責的 analytics worker（以排程觸發）定期匯總互動數據，供 FAQ 與儀表板端點使用。

## 4. 新前台規劃：如何打造豐富體驗？ (The "How" for the Frontend)

全新的 `apps/web` 和 `apps/admin` 將是使用者直接互動的門面，其規劃重點如下：

### 4.1. 豐富的內容呈現 (Hybrid Model)
- **目標**：兼顧結構化資料的清晰與敘事內容的生動。
- **做法**：頁面將同時從後端 API 獲取兩種類型的資料：來自 `.json` 的結構化資料（如價格、規格表）和來自 `.md` 的敘事性內容（如故事、心得），並將它們融合成一個體驗良好、富有吸引力的頁面。

### 4.2. 無縫的訂課系統連動
- **目標**：簡化使用者從瀏覽到預訂的流程。
- **做法**：前台網站的「立即預訂」按鈕，將負責將使用者平滑地重導向至訂課系統，並透過 URL 參數傳遞雪場、教練等上下文資訊，免去使用者重複選擇的麻煩。

### 4.3. 統一的管理與分析後台
- **目標**：提供一個強大、易用的一站式管理中心。
- **做法**：`apps/admin` 將是一個全新的單頁應用 (SPA)，它將取代舊的 `admin.html`，作為一個現代化的使用者介面，來操作和整合所有現有的後端 API 功能。它將：
    - **統一內容管理**：提供所有內容類型（雪場、教練、文章、優惠）的增刪改查介面。
    - **統一數據儀表板**：在一個介面中，同時呈現我們新的「使用者行為分析」和舊的「LLM 成本分析」，讓管理者對網站狀況有全面的了解。

## 5. 結論

透過「重用後端、革新前端」的核心策略，我們可以在充分利用現有資產的基礎上，解決目前平台面臨的所有核心挑戰。這份藍圖為我們提供了一條清晰、務實且可擴展的道路，以打造一個符合未來業務發展需求的、高品質的內容管理與分析平台。
